# v0.9.11 desktop recovery and menu-bar audit

## Trigger

After a computer restart, the live daemon returned automatically, but the owner
did not know that it had returned or how to turn it back on without developer
help. `launchd` made the system operationally durable while leaving the customer
experience fragile. The existing Store-track menu-bar shell could not solve
this: it is sandboxed, controls only its bundled helper, and intentionally does
not manage the released Python/Ollama edition.

## Audit

### Usability and customer experience

- A normal owner should not need to know `launchctl`, a service label, a plist
  location, a database path, or which process owns the local model.
- “The process exists” and “the product is healthy” are different claims. The
  menu shows background state continuously and runs the deeper database,
  queue, Telegram, model, and Calendar status only when asked.
- The main actions use product language: **Turn Hob On**, **Restart Hob**,
  **Check Health**, **Open Hob Log**, and **Show Hob Data Folder**.
- Quitting the menu-bar companion does not stop reminders; its help text says
  that Hob keeps running.
- The flame changes to a warning symbol when the service is absent or
  unavailable, and every color state also has text and an SF Symbol.

### Onboarding

- `scripts/setup.sh` now installs the durable service and native menu companion
  on macOS instead of ending with an instruction to start a foreground daemon.
- `scripts/install_macos.sh` is the repeatable install, update, and repair path.
  It builds and signs the app, launches it at login, creates the service when
  absent, and starts it only when a Telegram credential already exists.
- Existing daemon configuration wins over defaults. The installer carries the
  exact database, model, Ollama endpoint, and timezone into health checks.
- A legacy checkout database remains supported. If both legacy and app-data
  databases exist and no installed service or explicit path resolves the
  choice, installation stops instead of silently attaching to the wrong life.
- `scripts/hobctl` preserves a text-only and remote-session fallback with the
  same status/on/restart/log/install vocabulary.

### Bugs and feature robustness

- Start handles both a loaded-but-idle job and an installed-but-unloaded job.
  Restart fully unloads and reloads only the fixed user service.
- Replacing a running menu agent can briefly return launchd error 5 after
  `bootout`, even when the old job no longer appears loaded. Installation now
  bounds and retries that transition, accepting success only from a completed
  bootstrap—not from a dying job that is still briefly visible.
- Forced `kickstart -k` could overlap the replacement with the dying process's
  single-instance lease, producing a misleading success followed by launchd
  retries. Installer, menu-bar, and `hobctl` restarts now fully unload and
  reload the service. Text workflows wait for one stable PID before claiming
  Hob is back on.
- The older LaunchAgent supervised `uv`, which spawned the Python bot as a
  child. The bot could briefly outlive its wrapper and keep the Telegram lease.
  The installer now migrates both fresh and existing agents to supervise the
  virtualenv Python process directly while preserving the owner, schedule,
  planning preferences, database, and model.
- An absent plist is never synthesized by the menu itself; it reports Needs
  Setup. Installation remains an inspectable, testable operation.
- Existing daemon settings are preserved during an update while its executable
  is migrated safely. Prior app, daemon plist, and menu plist copies are
  retained before replacement.
- Live install verification exposed that `plutil -replace` can insert into a
  plist array instead of replacing its indexed value on the target macOS
  version. Plists are now rendered with `plistlib`, replacing
  `ProgramArguments` atomically. Cross-platform regression tests require one
  exact menu executable, the exact two daemon arguments, paths containing
  spaces, and no template placeholders.
- LaunchAgent output parsing is bounded to `state` and `pid`; no command output
  containing user data enters the UI.
- The health subprocess receives an explicit live database path, eliminating
  the ambiguous-database failure that made the raw `status` command confusing
  on this installation.
- A zero CLI exit is not overclaimed as ready: missing Telegram credentials,
  an unpaired owner, and durable queued work become explicit attention states.
- Unit tests cover running PID parsing, loaded-but-idle state, installed versus
  missing state, forced restart, bootstrap-before-start, credentials, pairing,
  queue attention, and a complete healthy result.

### Privacy and safety

- The companion reads no task or message records and stores no new task data.
- Health output is the existing privacy-safe aggregate status. The success
  summary names only subsystems.
- The Telegram token stays in Keychain and is never copied into either
  LaunchAgent.
- The menu can start or restart Hob but deliberately offers no one-click data
  deletion, restore, or service uninstall.

### Platform fit

The released Open Local edition now uses the macOS menu bar. The App Store
edition retains its distinct sandboxed `SMAppService` surface. ADR 0002 defines
the same states and actions for a future Windows system-tray companion, but
v0.9.11 does not claim Windows service or tray support.

## Release gates

- Shell syntax, plist lint, ten service/health unit tests, four installer
  rendering tests, release Swift build, existing App Store foundation tests,
  Xcode bundle build, Python tests, real-model interpreter and analysis evals,
  and Ubuntu/macOS CI pass on the release commit.
- Install over the existing live LaunchAgent without changing its database,
  model, owner, schedule, or planning configuration.
- The flame appears in the current graphical session and reports the same PID
  as `launchctl`.
- Use **Check Health**, then **Restart Hob**. Confirm a new PID, schema 10,
  paired Telegram owner, expected model, and clean queues.
- Log out/reboot evidence remains a 1.0 release-candidate gate; `RunAtLoad` plus
  the existing daemon `KeepAlive` is implementation evidence, not that manual
  journey.
