# v0.9.13 security-boundary audit

## Scope

This increment combines the Telegram trust-boundary and local security
hardening work audited in
[`telegram-security-increment.md`](telegram-security-increment.md) and
[`local-security-hardening-increment.md`](local-security-hardening-increment.md).

## Customer outcome

- A Telegram stranger or group can no longer claim a fresh Hob. The intended
  owner sends `/start` to learn their ID, authorizes it once on the Mac, then
  continues the existing guided setup. Upgraded paired owners do nothing.
- Messages, captions, callbacks, and reactions share the same private-chat
  owner boundary. Unauthorized and Telegram service updates are discarded
  without retaining content or generating denial noise.
- Databases, SQLite sidecars, locks, backups, exports, restore candidates, and
  four bounded log generations are owner-only. Existing default data tightens
  automatically when opened.
- Local Ollama remains unchanged. A non-loopback model server requires an
  explicit setting, HTTPS, and visible health warnings that task text leaves
  the Mac.
- Setup uses the committed dependency lock, CI actions are immutable, CI scans
  the frozen runtime graph, and Dependabot watches Python and Actions updates.
- Keychain token updates use Security.framework; the secret is not placed in a
  child process argument.

## Usability and onboarding audit

The security boundary adds one Terminal command only for the Open Local
edition's first owner. `/start` provides the exact command and the next
`/start` resumes onboarding. This is a deliberate intermediate constraint; a
no-Terminal ownership flow remains part of the App Store edition's 1.0 gate.
Every existing daily-use command, task interpretation, digest, recap, and
recovery path remains unchanged.

Remote inference fails before startup with an actionable privacy explanation.
The install and menu preserve the opt-in across reboot. Health output keeps the
remote boundary visible instead of treating it as an invisible advanced option.

## Robustness evidence

- Schema 11 migrates reply anchors to `(chat_id, message_id)` and timestamps
  them under the stored owner chat.
- Completed inbox, outbox, and reply-reference history is retained for 30 days
  and capped at 1,000 rows per table. Pending work is never pruned.
- Permission tests run with a deliberately permissive umask and cover live
  SQLite files, locks, backup, restore, export, and log rollover.
- Malformed, credential-bearing, path-bearing, non-opted-in remote, and remote
  HTTP Ollama endpoints fail closed. Localhost IPv4, IPv6, and `.localhost`
  remain supported.
- The exact release commit must pass the Python suite, both Swift packages, the
  optimized menu build, Xcode app build, shell/plist checks, frozen dependency
  audit, real 14B-model corpora, GitHub macOS/Ubuntu CI, backup, install, restart,
  and live privacy-safe health before the release is considered deployed.

## Remaining 1.0 work

This release closes the read-only security audit's concrete findings. The 1.0
acceptance matrix still requires no-Terminal Store onboarding, queue recovery,
DST and Calendar permission rehearsals, accessibility evidence, upgrade and
rollback drills, sustained-size measurements, model-baseline evidence, and the
seven-day daily-use loop. Homebrew formulae and Ollama model tags remain mutable
upstream inputs; deployment evidence records the installed model digest.
